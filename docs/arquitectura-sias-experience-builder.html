Razones que originaron el cambio

La solución anterior dependía de supuestos que dejaron de ser confiables

El diseño funcionaba mientras existiera una sola carga por correo y cada componente respondiera en el orden esperado. Esa condición no era segura frente a cargas simultáneas, reintentos o más de un elemento en el Dashboard.

Dependencia de Web AppBuilder

El mapa se abría dentro del Dashboard mediante una aplicación Web AppBuilder, pasando token y extensión por URL. Esa aplicación está prevista para salir de operación y dejó de ser una base confiable para evolucionar el proceso.

Corrección: mapa nativo dentro del widget Experience Builder

Solo una carga utilizable por correo

El correo actuaba como selector. Si el mismo correo tenía dos cargas, el filtro o parámetro del Dashboard listaba más de una caja/elemento y no podía identificar inequívocamente cuál correspondía.

Corrección: selección exclusiva por GlobalID

La carga nueva reemplazaba contexto anterior

Para sostener el supuesto “un correo = un registro”, la herramienta de carga eliminaba temporales anteriores del mismo correo. Esto impedía reintentos y sesiones paralelas válidas.

Corrección: cargas independientes aunque el correo se repita

Ingreso elegido por deducción

La GP final no recibía el ObjectID o GlobalID seleccionado. Intentaba deducir qué registro acababa de entrar, con riesgo de procesar otro si dos usuarios trabajaban al mismo tiempo.

Corrección: parámetro registro_id obligatorio

Ejecución de GP fuera de la experiencia

El usuario no tenía dentro de la aplicación una vista completa del job, sus etapas, mensajes o errores. Era difícil saber si el formulario se guardó y si el ingreso seguía ejecutándose.

Corrección: seguimiento del job y siete etapas visibles

Limpieza temporal no garantizada

El flujo podía copiar información a la capa productiva sin retirar de forma controlada el registro de ingreso, dejando residuos y aumentando la ambigüedad de futuras búsquedas.

Corrección: verificar producción y eliminar exactamente el temporal procesado

Lectura frágil de archivos KML

La carga dependía de una estructura XML y un namespace específicos. Algunos exportadores guardan el polígono dentro de Folder o MultiGeometry, omiten declaraciones XML o entregan un KMZ, provocando fallas aunque las coordenadas fueran válidas.

Corrección: parser independiente del namespace y soporte integral KML/KMZ

Stepper funcional

Recorrido completo de una solicitud

  1. Validación inicial

    Correo y confirmación deben coincidir; se valida extensión, tamaño del KML/KMZ y control humano deslizante.

  2. Carga del archivo

    El widget utiliza la capacidad UPLOADS del GPServer y obtiene un itemID temporal.

  3. GP de carga

    La GP abre el KML o KMZ, localiza todos los Polygon y sus anillos, crea una entidad temporal independiente y calcula gerencias, extensión y tokens.

  4. Contrato de sesión

    El widget recupera globalid, token y map_token. Si falta uno, el flujo no continúa.

  5. Mapa aislado

    Se habilita el mapa, se filtra la capa de ingreso por GlobalID, se resalta el polígono y se ajusta la extensión.

  6. Edición Survey123

    El formulario se abre automáticamente con mode=edit, GlobalID y token de edición.

  7. Confirmación de envío

    La API de Survey123 emite onFormSubmitted; el widget evita disparos duplicados y llama la GP final.

  8. Ingreso productivo

    La GP recibe el identificador exacto, ejecuta siete etapas, verifica producción y elimina solo ese temporal.

El geoproceso final ahora es visible desde la aplicación: cuando Survey123 confirma el envío, el widget obtiene el jobId, consulta su estado, presenta los mensajes emitidos por cada una de las siete etapas y muestra éxito o error sin sacar al usuario de Experience Builder.

Normalización geométrica

Compatibilidad ampliada para KML y KMZ

La GP ya no busca una ruta XML fija. Recorre la estructura por el nombre local de las etiquetas hasta obtener el arreglo de coordenadas que forma el polígono y su envolvente.

✓ Validado en servidor
Estructuras admitidas

Document, Folder, Placemark, MultiGeometry y uno o varios elementos Polygon.

XML tolerante

Procesa KML con o sin namespace y completa en memoria prefijos utilizados pero no declarados, como xsi.

KMZ completo

Inspecciona los documentos .kml internos aunque no se llamen doc.kml o se encuentren dentro de subcarpetas.

Geometría ArcGIS

Valida coordenadas WGS84, cierra los anillos y normaliza la orientación de exteriores y huecos antes de crear el Polygon.

1Validar extensión y tamaño
2Abrir KML o descomprimir KMZ
3Completar prefijos XML
4Recorrer todos los Polygon
5Extraer longitud y latitud
6Normalizar anillos
7Crear geometría y extent
Control de seguridad: el KMZ limita a 100 los documentos KML internos y a 50 MB el XML total descomprimido. Si no existe un polígono válido o las coordenadas están fuera de WGS84, la carga se detiene antes de crear el registro temporal.

Reglas de integridad

Qué garantiza la nueva versión

El correo no es una clave

Puede repetirse. Las decisiones técnicas se realizan con ObjectID o, preferentemente, GlobalID.

El GlobalID permanece durante toda la sesión

Es el mismo valor usado por el mapa, Survey123 y la GP final.

Los tokens son temporales y específicos

El widget no documenta valores reales y en consola solo muestra una versión enmascarada.

La limpieza es posterior a la confirmación

Si falla Power Automate o la verificación productiva, el temporal se conserva para revisión segura.

Conclusión

La modernización cumple el objetivo

La solución dejó de depender del orden de llegada, del correo como selector, de una estructura KML rígida y de integraciones separadas sin confirmación. El nuevo widget acepta KML/KMZ, controla el mapa, la edición en Survey123 y la ejecución de las GP Tools con un identificador inequívoco, permitiendo cargas paralelas y una limpieza segura del registro temporal.
